## 2. Key Learnings

### Firing Alert Triage Pattern: All-Four-Golden-Signals Means Infrastructure
When all four golden signal alerts (latency, traffic-absent, error-rate, saturation) fire simultaneously for the same service, the root cause is almost never the service itself. Look first at:
- Shared downstream dependencies (databases, message queues, caches)
- Infrastructure-layer failures (node pressure, network partitions, cloud provider events)
- Recent deployments that changed resource limits or networking config

The `inventory-service` and `order-processor` alerts today match this pattern exactly.

### health=error on Alert Rules Signals Evaluation Failure, Not Just Alerting
`health=error` on a rule means the alert *evaluation itself* failed (datasource unreachable, query timeout, bad PromQL). It is distinct from `state=firing`. When you see both simultaneously, treat it as a signal that the observability layer itself may be degraded — the alert may be firing on stale data.

### SHA Requirement for GitHub File Updates
`create_or_update_file` requires a blob SHA for existing files. The correct flow:
1. `get_file_contents` (no line_range) — returns the SHA in the response header.
2. Pass that SHA to `create_or_update_file`.
Omitting the SHA returns a 422 error ("SHA does not match the file").

### manage_automations Is Blocked in Automation-Triggered Runs
By design, Grafana Assistant blocks `manage_automations` when the session itself was triggered by an automation. This prevents self-modification loops. Automation metadata must be sourced from skills or external documentation during automated runs.

### SLO Burn Rate Alert Naming Convention
Grafana SLO auto-generates exactly two alert rules per SLO: `*- Error Budget Burn Rate is Very High` and `*- Error Budget Burn Rate is High`. These map to the fast-burn (1h window) and slow-burn (6h window) detection windows respectively. Both firing at the same time indicates rapid budget exhaustion.

### Date Convention for Digest Filenames
Always derive the filename date from `time_iso_local` (user's local timezone), never from UTC. At 11:50 PM ET on July 3rd, the UTC timestamp reads July 4th — using UTC would produce the wrong filename.

## 3. How Enterprise Customers Use This at Scale

### All-Golden-Signals Alerting Across Every Service
Enterprise platform teams define golden-signal alert groups (latency-p99, traffic-absent, error-rate, saturation) as a standard template deployed across every service at onboarding time. At scale:
- Alert rules are defined in Terraform/Jsonnet/Grizzly and committed to a central alert-rules repo.
- New services inherit the template via a service-onboarding pipeline that stamps the team, service, and environment labels.
- Platform SRE reviews weekly to ensure every production service has all four golden signals covered.
- Silences and routing policies are managed centrally; teams can add receivers but cannot remove the platform defaults.

### SLO as the Contractual Interface Between Teams
At scale, SLOs replace ad-hoc alerting as the primary reliability contract:
- Platform engineering defines the SLO framework (metric family, window sizes, burn rate thresholds).
- Service teams own their SLO targets and error budget policies.
- Exec dashboards show error budget health across all services in a single view.
- When a team deploys and their SLO burn rate spikes, the deploy is automatically flagged in post-deploy checks — no separate QA step required.
- HealthCo's pattern (cardiology-api, oncology-api, order-service, checkout service each with separate Availability and Latency SLOs) is the recommended model: one SLO per signal type, not one omnibus SLO per service.

### Multi-Team Skill Libraries as a Living Knowledge Base
Enterprise customers maintain `scope: "tenant"` skill libraries with 50–200 entries:
- Every critical service has a runbook skill (escalation paths, known failure modes, PromQL for triage).
- Post-mortem learnings are promoted into skills after each major incident.
- Skills reference dashboard UIDs so engineers navigate directly to the right panel.
- Quarterly skill audits retire stale entries and refresh with current metric names.
- New engineers complete onboarding by working through the skill library with Grafana Assistant — no shadow period with a senior engineer required.

### Automated Digest Pipeline as Shift Handoff Infrastructure
Mature SRE orgs replace manual shift handoff documents with automated digest pipelines:
- Pre-shift digest committed at 07:50 AM before standups.
- Post-shift digest at 23:50 PM captures overnight events.
- Separate digest templates per domain: infra, application, security, cost.
- Each team's digest commits to a team-owned subdirectory in a shared observability monorepo.
- Digest content feeds into a weekly rollup report sent to engineering leadership automatically.

### GitOps Documentation at Enterprise Scale
The GitHub MCP commit pattern scales into a full observability knowledge base:
- **Runbooks**: Auto-drafted from investigation summaries; engineers review and merge via PR.
- **Post-mortems**: Generated from IRM incident timelines; PR creation triggers Slack notification to stakeholders.
- **Architecture Decision Records**: Infrastructure decisions captured as ADRs in `/docs/adr/`.
- **Compliance audit trail**: Git commit history provides timestamped, tamper-evident records for HIPAA operational reviews, SOC 2 Type II evidence collection, and ISO 27001 control documentation.

### Health=Error Alert Governance
Enterprise alerting governance teams create a dedicated alert rule group for evaluation health:
- A recording rule tracks `grafana_alerting_rule_evaluations_total{state="error"}`.
- A meta-alert fires when any production rule is in `health=error` for >5 minutes.
- Runbook links the on-call engineer directly to the datasource's scrape health dashboard.
- Resolution is tracked as an SLO breach for the observability platform itself — the platform team is accountable for keeping evaluation health green.
