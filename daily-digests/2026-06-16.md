## 3. How Enterprise Customers Use This at Scale

### Multi-Burn-Rate SLO Alerting

**Architecture at Scale:**
- **Multi-Team Ownership:** Platform SRE team owns SLO framework (recording rules, alert templates), product teams own SLO definitions (objectives, query expressions). Centralized folder structure (`cfhxob0gc5zpcb`) enables policy as code with Terraform or Grizzly.
- **Cross-Cluster Federation:** Recording rules pre-aggregate across clusters before evaluating alerts. Enterprises with multi-region deployments use Grafana Mimir's global view to compute SLOs across all regions simultaneously, avoiding per-region alert storms.
- **Cardinality Management:** The `by()` clauses in SLO recording rules carefully control label propagation. At scale, teams exclude high-cardinality labels (user_id, request_id) from SLI series to keep recording rule output under 10k series per SLO.

**Operational Workflows:**
- **Runbook Automation:** Each burn rate alert links to context-aware runbooks via `grafana_slo_info` labels. On-call engineers query `grafana_slo_objective` to calculate remaining error budget in seconds, automating the "should I page someone?" decision.
- **Error Budget Reviews:** Weekly SLO review meetings use pre-built dashboards querying `grafana_slo_sli_window` to visualize burn trends. Product and engineering leaders negotiate feature velocity vs. reliability trade-offs using quantified error budget data.
- **Incident Severity Mapping:** Very High burn rate alerts (1-hour window) trigger SEV-1 pages; High burn rate alerts (6-hour window) create tickets for business-hours review. This two-tier approach balances MTTR with on-call health.

**Team Structure:**
- **Platform Engineering:** Maintains recording rule infrastructure, upgrades Grafana SLO plugin, tunes burn rate thresholds based on MTTR data.
- **Service Owners:** Define SLIs (what queries), SLOs (what thresholds), and notification policies (who gets paged). Use Grafana SLO UI for self-service configuration.
- **SRE Embedded Teams:** Review SLO compliance in postmortems, propose new SLOs for under-monitored user journeys, advocate for error budget-based release gating.

### GCP Managed Service Monitoring

**Architecture at Scale:**
- **Multi-Project Monitoring:** Enterprises with 50+ GCP projects use Prometheus federation or Grafana Agent's remote_write to centralize metrics. Alert rules use `project_id` label to route notifications to owning teams.
- **Cost Optimization:** Cloud SQL monitoring uses `database_id` label to track per-database costs. Teams correlate high connection counts or CPU with BigQuery billing exports to identify expensive queries.
- **Compliance Integration:** HIPAA-regulated healthcare environments (like HealthCo) export Cloud SQL audit logs to Loki, then correlate alert events with access logs for compliance reporting. Disk usage alerts feed capacity planning models required for SOC 2 continuous monitoring controls.

**Operational Workflows:**
- **Capacity Planning:** `GcpCloudSQLDiskUsage` alerts feed FinOps dashboards. When disk utilization crosses 70%, automated workflows file Jira tickets for database team to provision larger instances or archive old data.
- **Replication Lag Handling:** `GcpCloudSQLLagSecondsBehindMaster` alerts route to database oncall. Runbooks include "check for long-running transactions" and "validate replica instance size." At scale, teams auto-remediate by restarting hung replication via GCP API.
- **Pub/Sub Queue Health:** `GcpPubSubNumUndeliveredMessages` alerts integrate with autoscaling policies. When undelivered message count exceeds threshold, Kubernetes HPA scales consumer pods; alert annotations include current consumer count for context.

### Machine Learning Anomaly Detection

**Architecture at Scale:**
- **Model Training:** Adaptive Metrics/Traces in Grafana Cloud trains models on 30 days of baseline data. Enterprises with seasonal traffic (e.g., healthcare enrollment periods) use separate models per season or manually adjust sensitivity during known high-traffic events.
- **Multi-Signal Correlation:** ML alerts on traces (latency anomalies) correlate with traditional threshold alerts on metrics (error rate, CPU). Correlation dashboards show whether an anomaly triggered an SLO burn or was a false positive.
- **Alert Tuning:** Teams start with ML alerts in "observe" mode (create annotations, don't page). After 2-4 weeks of validation, promote to paging alerts. This reduces ML false positive fatigue during rollout.

**Volume Considerations:**
- **Trace Sampling:** ML models train on sampled traces (typically 10-20% sampling rate for high-throughput services). Enterprises balance model accuracy with ingestion costs by using tail-based sampling (keep all error traces, sample success traces).
- **Cardinality Explosion:** ML-generated labels (anomaly_score, anomaly_type) add cardinality. At scale, teams use label_keep/label_drop in recording rules to prevent ML metadata from propagating to long-term storage.

### GitHub-Backed Configuration Management

**Architecture at Scale:**
