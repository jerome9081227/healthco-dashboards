### Alert State: Unknown ≠ Firing
`state: unknown` in Grafana alert rules means the backend has not yet computed or reported the current state. Common causes: datasource temporarily unreachable, rule group paused, or newly created rule not yet evaluated. Distinguishing unknown from firing requires querying the datasource directly with the rule's PromQL.

## 3. How Enterprise Customers Use This at Scale

### Multi-Domain SLO Architecture for Healthcare
Large healthcare enterprises organize SLOs into **domain-isolated folders** with separate ownership, error budget policies, and escalation paths — mirroring clinical department structures:

- Cardiology SREs own cardiology SLO folders; oncology SREs own oncology folders. Alerts never cross domain boundaries, preventing alert fatigue and ownership ambiguity.
- Multi-window burn rate alerting (High burn = ticket; Very High burn = page) prevents SLO breaches from producing one-size-fits-all noise.
- Executive compliance dashboards roll up all domain SLOs into a single health panel — CISO and CTO see reliability posture without needing to understand PromQL.
- For HIPAA environments, folder-level RBAC ensures minimum-necessary data access: a cardiology engineer cannot view oncology alert details.

### Golden Signals as Platform-Managed Templates
Enterprises deploy golden signal alert templates (latency-p99, error-rate, traffic-absent, saturation) as **reusable Terraform/Jsonnet/Helm modules** applied consistently across 50–500+ services:

- Platform engineering owns the template; application teams supply service-specific thresholds via configuration.
- `traffic-absent` alerts are often the most valuable: they catch "dead service" scenarios where error-rate alerts produce zero signal (no traffic = no errors = no pages, but the service is down).
- Saturation alerts feed auto-scaling policies in GCP/AWS — triggered before SLOs degrade rather than after.
- At scale, a single golden signal template update rolls out to all services simultaneously, replacing weeks of manual alert maintenance.

### Dual Automation: Snapshot + Refresh Pattern
Enterprises run staggered automations to handle data ingestion lag and end-of-day reporting completeness:

- Early run (11:00 PM) captures most of the day's activity, commits a baseline.
- Late run (11:50 PM) refreshes with any stragglers and finalizes the record.
- Both commits are version-controlled — git history provides a timestamped record of what was known at each point in time.
- This pattern also works for shift-handoff documentation in 24/7 NOC environments: each shift produces a commit at handoff time, creating a durable searchable log.

### GitHub as the Observability Source of Truth
Platform teams configure the GitHub MCP at the tenant level so all observability artifacts (dashboards, alert rules, SLO definitions, runbooks, post-mortems) live in Git:

- Every Grafana change triggered from an assistant session produces a commit — no more "shadow dashboards" built manually and never versioned.
- PRs for alert threshold changes enforce peer review before production impact.
- GitHub Actions validate JSON syntax and PromQL expressions before merge, catching syntax errors that would otherwise silently fail in Grafana.
- Teams with 50+ dashboards use Git blame to answer "who changed this panel and why?" — replacing Slack archaeology.

### Skills as Institutional Memory at Scale
Enterprises build skill libraries that persist beyond employee tenure and supplement training programs:

- Alert runbooks stored as skills eliminate the "tribal knowledge" problem — new engineers get the same triage guidance as 5-year veterans, immediately.
- Skills are updated after every post-mortem, closing the loop between incidents and operational documentation with zero additional process overhead.
- A "Skills Guild" (platform + SRE + AppDev representatives) reviews and approves new skills quarterly, treating them with the same rigor as code.
- Volume: Large tenants maintain 50–200 skills covering every major alert pattern, integration, and service — a queryable institutional brain.
