## 3. How Enterprise Customers Use This at Scale

- **Golden-signal-per-service as a standing template**: the exact structure seen here — one folder/group per service, 4 rules per group (latency, traffic, errors, saturation) — is how large platform teams standardize alerting for every new service at onboarding, usually enforced via alert-as-code (Terraform/Grafana provisioning) rather than manual creation, so the pattern scales to hundreds of services without drift.
- **Correlation before paging**: mature SRE orgs add a correlation layer (shared label, deploy ID, or dependency graph) so a wide, simultaneous firing pattern like today's 8-service/32-rule event collapses into one incident with one owner — instead of generating 8 separate pages that get triaged in isolation.
- **Multi-window SLO burn-rate as the standard over static thresholds**: the `order-service Latency` Very-High/High burn-rate pair mirrors how enterprises route fast-burn to paging and slow-burn to ticketing on the same SLO, cutting noise without losing sensitivity to gradual regressions.
- **Stale-incident hygiene at scale**: enterprises running high incident volume (weekly or higher) enforce automatic incident timeout/auto-resolve policies specifically to avoid the kind of 2-month-old "active" incidents seen here (`jojoj`, `herlllo`) — a small process gap that compounds into audit noise as incident count grows.
- **GitOps-audited configuration snapshots**: committing a timestamped, tool-verified state check to a repo (as this digest does) is a lightweight pattern platform teams use for change-management evidence — valuable because it re-queries live state every run instead of trusting a cached assumption, which is exactly what confirmed the `KubePodCrashLooping` delta today.
