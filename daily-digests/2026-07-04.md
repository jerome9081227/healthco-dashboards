### The Dual Burn-Rate SLO Alert Architecture
Every Grafana SLO generates exactly two alert rules: "Very High" (fast burn, short window — designed for immediate paging) and "High" (slow burn, longer window — designed for early warning tickets). These two rules should route to different contact points in the notification policy: the "Very High" rule pages oncall; the "High" rule creates a ticket. Treating them identically creates alert fatigue.

## 3. How Enterprise Customers Use This at Scale

### Golden Signal Alert Libraries Across 100+ Services
Large healthcare and e-commerce enterprises implement golden signal alert libraries (rate, errors, latency, saturation) as a shared Terraform or Jsonnet module deployed uniformly across every microservice. Teams register new services by adding one configuration entry; the module auto-generates all four alert rules without manual PromQL authoring. This approach:
- Ensures every service has baseline coverage from deployment day zero
- Reduces alert authoring time from hours to minutes per service
- Makes compliance audits simple — compare service registry vs. alert rule inventory

### SLO-as-Code for 100+ Services
Enterprises with 100+ microservices automate SLO creation via the Grafana SLO API or Terraform provider, feeding from a service catalog. Each entry defines the SLI type (availability or latency), objective, and window; the pipeline creates the SLO, recording rules, and dual burn-rate alert rules automatically. Platform engineering maintains the pipeline; application teams own the objective values. At scale:
- A new service gets full SLO coverage within minutes of catalog registration
- SLO objectives are version-controlled alongside application code
- Burn rate alert routing is standardized: "Very High" pages oncall, "High" files a ticket

### Domain-Scoped RBAC for Regulated Industries
The folder-per-domain pattern visible in HealthCo (cardiology, oncology, order-service in separate folders) scales directly to enterprise RBAC:
- Each folder maps to an LDAP/SSO group — cardiology engineers own their alert rules, oncology engineers own theirs
- Platform engineering retains cross-folder read access for incident response
- Grafana's audit log captures every rule change with user identity, timestamp, and diff
- For HIPAA change management: the audit log plus daily digest commits constitute an immutable, reviewable change trail without manual documentation

### Runbook-as-Skill Lifecycle at Enterprise Scale
Enterprises manage 50–200 runbooks in the Grafana Assistant skills knowledgebase, organized by domain. Lifecycle:
1. SRE writes the runbook during an incident (15 min)
2. Runbook is reviewed and committed to `skills/` in the mono-repo
3. A GitHub Action syncs repo skills to Grafana Assistant tenant-level skills
4. All engineers inherit the runbook automatically on next investigation — no Confluence search, no Slack archaeology

### Layered Automation Summarization Pattern
The two-automation pattern in HealthCo (11:00 PM raw insights + 11:50 PM structured digest) scales to a full enterprise reporting hierarchy:
- Team-level nightly digests → squad-level weekly rollup → department-level monthly summary
- Each level commits to a different directory in the mono-repo
- Engineering leadership reads the monthly file as their AI observability executive summary — no manual reporting, no slide deck preparation
