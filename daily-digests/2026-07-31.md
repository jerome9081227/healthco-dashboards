## 2. Key Learnings

- **Conversation history is not a current tool capability.** There is no Grafana Assistant tool to list or read past chat sessions with a given user. The Agent Observability tools (`agento11y_*`) only track externally instrumented demo/test agents (`sigil-demo`, `my-custom-agent`, etc.) — not Grafana Assistant's own conversations — so they cannot substitute for a transcript store. This was already flagged as a feature request in the "Daily Learnings" skill; treat it as a known, standing gap rather than re-discovering it each run.
- **Health=error is a distinct failure mode from a threshold breach**, and it clusters. The same 8 service golden-signal groups have shown `health=error` for at least two consecutive days — a broad, correlated health=error pattern across independently-defined rule groups is a strong signal of one shared upstream fault (e.g., a broken recording rule, datasource, or query template reused across service scaffolding) rather than 8 real simultaneous outages. Investigate the shared generator/template before triaging each service individually.
- **Reference skills decay.** The "HealthCo Grafana Environment Reference" skill (dated 2026-06-06) is now materially out of date against live alert-rule and SLO inventory. ## 3. How Enterprise Customers Use This at Scale

- **Architecture**: Enterprises running 200+ alert rules across many service folders (as seen here: order-service, inventory-service, order-processor, shipping-service, checkout-service, fraud-detection, payment-gateway, auth-service, notification-service, cardiology-api, oncology-api) typically generate golden-signal rule sets from a shared template/module per service, with multi-window SLO burn-rate alerting layered on top for the services closest to revenue or patient care.
- **Operational workflows**: When a template-generated rule family fails across many services at once (this environment's 8-service `health=error` cluster), mature SRE practice is to page the platform/tooling owner for the shared template first, and suppress per-service noise via a single upstream fix rather than 8 parallel tickets — otherwise on-call burns hours chasing 32 symptomatic alerts instead of 1 root cause.
- **Team structures**: Platform/SRE owns the rule-generation template, alerting pipeline, and the digest/automation tooling itself; service teams own thresholds and business logic; a documentation/knowledge-base owner (or rotation) is responsible for keeping environment-reference skills in sync with the live stack so automated tooling (digests, investigations, on-call runbooks) doesn't reason from stale facts.
- **Volume considerations**: At 200+ rules and growing (58 → 203+ in under two months per this environment's own history), enterprises typically add rule-inventory diffing/linting to CI, cap SLO recording-rule sprawl (each SLO here generates ~15 recording rules), and version-control knowledge-base/skill content alongside the infrastructure it describes.
