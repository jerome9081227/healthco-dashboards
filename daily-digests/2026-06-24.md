## 3. How Enterprise Customers Use This at Scale

### Federated Alert Rule Management Across Teams
At 200+ rules and growing, enterprise customers organize alert rules into a folder hierarchy that mirrors their org chart:
- **Folder per team** (`cardiology-api`, `oncology-api`, `order-service`) with a dedicated SRE or AppDev owner for each
- **Platform-managed folders** (`cloud-provider---gcp`, `grafanacloud-ml`) owned by the central platform engineering team, managed via Terraform
- **Cross-team review gate**: Alert rule changes require a PR review from the folder owner before Terraform apply
- **Automated rule audit**: The nightly digest automation lists all rules, compares against the last snapshot, and posts a delta (added/removed/state-changed) to the platform Slack channel

This model scales to 500+ rules across 30+ teams without a central bottleneck — each team manages their alert rules as code in their own repo path.

### SLO Error Budget as a Cross-Functional Governance Tool
The HealthCo SLO model (6 SLO groups across cardiology, oncology, order-service, and frontend) maps directly to enterprise governance patterns:
- **Product and engineering shared ownership**: Product managers own the SLO target; SREs own the alerting and error budget response
- **Monthly error budget review**: Digest automation generates a monthly SLO summary committed to the repo; used in product retrospectives to justify reliability investment vs. feature velocity
- **SLA traceability**: For healthcare customers, SLO error budgets map to contractual SLA commitments. The GitHub commit history is the audit trail showing SLO compliance was actively monitored.
- **Automatic reliability sprint trigger**: When error budget drops below 20%, an automation posts a Jira ticket via MCP to create a reliability sprint — no manual triage meeting required.

### Multi-Cluster Alert Rule Normalization
Enterprise healthcare organizations run Grafana across 5–15 clusters (prod, staging, DR, region-specific HIPAA-scoped clusters):
- **Normalized alert rule templates** defined once, applied via Grafana Terraform Provider to all clusters
- **Cluster-specific thresholds** encoded as Terraform variables — the same rule fires at different thresholds in prod vs. staging
- **Cross-cluster digest**: The nightly automation queries each cluster's alert rule state via multi-datasource PromQL and produces a unified digest showing rule health across all clusters
- **Drift detection**: Any deviation between a cluster's live rules and the Terraform-managed canonical set is flagged in the digest as a configuration drift event

### Runbook Lifecycle Tied to Alert Rule Lifecycle
Mature platform teams implement a runbook-per-rule lifecycle:
1. Alert rule created → Grafana Assistant generates a draft runbook skill based on the rule's PromQL, labels, and thresholds
2. On-call engineer reviews and enriches the skill with observed triage steps after the first real alert
3. Alert enrichment is configured to attach the skill as a LogQL query and investigation trigger at rule creation time
4. Runbook skill is updated after each incident postmortem — the git history of the daily digest captures which rules were refined on which date
5. Alert rule deletion → skill is archived (not deleted) for compliance — the historical triage record is preserved

### Volume Considerations
- **Cardinality**: 203 rules × multi-window SLI recording rules = 1,600+ Prometheus time series for SLO alone; use Adaptive Metrics to aggregate SLI recording rules by service/window to cut cardinality by 40–60%
- **Log retention**: Loki retention scoped to 30 days for dev/staging, 90 days for prod, 365 days for compliance-tagged clinical API logs
- **Trace sampling**: Tempo head-based sampling at 10% for high-volume services (order-processor, inventory-service); tail-based sampling at 100% for error traces on cardiology-api and oncology-api
- **Digest storage**: At ~10KB per daily digest × 365 days = 3.65 MB/year in GitHub — negligible; the value is the searchable history, not the storage cost
