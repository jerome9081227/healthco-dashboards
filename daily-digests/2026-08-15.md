## 3. How Enterprise Customers Use This at Scale

**Golden-signal alerting per service (ACI Golden Signals pattern)**
Large customers standardize a small alert-rule template (error rate, latency, traffic/saturation) and apply it per service via provisioning-as-code, rather than hand-authoring rules per team. This keeps hundreds of services consistent and lets a single on-call rotation understand any team's dashboard at a glance. Ownership is typically split: platform engineering owns the template and notification-policy routing tree; each service team owns thresholds and labels.

**SLO/error-budget stacks**
Enterprises with dozens of services (as HealthCo already has with aci-* and order-service SLOs) centralize SLO definitions so error budgets roll up to a per-domain and org-wide reliability scorecard. SRE teams use burn-rate alerts (fast burn vs. slow burn) to distinguish "page now" from "file a ticket," which is the main lever for reducing alert fatigue at scale.

**Skills / runbooks as a managed library**
At scale, skills/runbooks move from individual notes to a version-controlled, peer-reviewed library (often in the same repo pattern used here — a dashboards/runbooks Git repo with PR review), with a defined owner per runbook and a periodic staleness review tied to incident postmortems.

**Automations and daily digests**
Enterprises use scheduled assistant automations to produce daily/weekly rollups per team or per service domain, routed to Slack/email and archived to Git for audit purposes — separating "what changed" (config diffs) from "what's currently unhealthy" (state snapshot), which this digest format mirrors.

**MCP / integration governance**
Multi-team orgs typically restrict which MCP servers and datasources are available per workspace/team, and require automations that write to external systems (like this GitHub commit step) to run under a scoped, auditable identity rather than a personal token.
