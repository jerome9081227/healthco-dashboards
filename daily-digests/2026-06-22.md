**Automation context restrictions are important to know.**
`manage_automations` is not available inside an automation-triggered run — list/get/run operations fail. Design automation prompts so they do not depend on self-inspection.

**Alert rule health state is the first triage signal.**
The live rule list shows cardiology-api SLOs in `state: normal` — a healthy confirmation. Rules showing `state: unknown` (oncology-api, order-service) indicate the evaluator health has not yet been resolved; this warrants a follow-up `alerting_manage_rules get` call for each UID.

**Multi-window SLI recording rules are the scaffolding behind every Grafana SLO.**
Each SLO generates ~11 recording rules (5m, 30m, 1h, 2h, 6h, 1d, 3d windows + info/objective/objective_window_seconds). These are read-only infrastructure — do not attempt to modify them directly; update the SLO definition instead.

**Golden signal alert groups follow a consistent naming convention.**
The pattern `{service}-{signal}-{qualifier}` (e.g., `inventory-service-latency-p99`, `order-processor-traffic-absent`) makes programmatic alert discovery reliable — useful for bulk operations or automated runbook lookup via the Assistant.

## 3. How Enterprise Customers Use This at Scale

### SLO Architecture at Scale
Large healthcare platforms (50+ services) define SLOs at the service boundary level — one SLO per API per signal type (availability + latency). Grafana SLO auto-generates the full multi-window recording rule set, keeping PromQL complexity out of individual team hands. Platform engineering owns the SLO template; AppDev teams provision instances via Terraform or the Grafana API.

**At scale:** A central SLO registry (Git-backed) lists every service SLO. A weekly digest (like this one) surfaces which SLOs are in `state: unknown` vs. `normal` — enabling platform teams to triage health evaluation gaps without clicking through 200 rules manually.

### Golden Signal Alert Groups as Operational Contract
The `{service}-{signal}-{qualifier}` naming pattern becomes an enforceable contract at scale. Platform engineering provides a baseline alert template; AppDev teams fill in thresholds. Compliance teams can audit coverage by running a simple `alerting_manage_rules list` and verifying that all four golden signals (latency, errors, traffic, saturation) exist for every registered service.

**At scale:** A monthly "alert coverage report" is generated by the digest automation, listing services missing one or more golden signal rules. This drives SRE quarterly OKRs around alert coverage percentage.

### GitOps for Observability Artifacts
Every dashboard, alert rule, and SLO definition is stored as code in `jerome9081227/healthco-dashboards`. Daily digests committed to `daily-digests/` provide a human-readable changelog alongside the machine-readable JSON/YAML. Teams use PR reviews to approve alert threshold changes — preventing alert fatigue from undisciplined noise increases.

**At scale:** Multi-cluster environments add a `cluster/` prefix to the repo path (`daily-digests/prod-us-east/2026-06-22.md`), enabling per-cluster digest comparison and federated SLO tracking across regions.

### Healthcare-Specific Compliance Workflows
`cardiology-api` and `oncology-api` SLOs are explicitly separated into their own folders (`afmhi9j11jwg0c`, `efmhi9j1bjhttc`), reflecting patient-critical service isolation. At scale, folder-level RBAC ensures only credentialed teams can modify these rules — supporting HIPAA minimum necessary access requirements.

**At scale:** Regulated service SLOs are tagged with `compliance:hipaa` and `data-class:phi-adjacent` labels. Alert notifications for these services route through a dedicated contact point with a separate on-call rotation, audit-logged separately from general engineering alerts.

## 4. Real-World Business Impact

### MTTR Reduction via SLO Burn-Rate Alerting
Multi-window burn-rate alerts (the Very High / High pairs per SLO) give on-call engineers a 1-hour warning before a 30-day error budget is materially impacted. Teams using this pattern report **MTTR reductions of 35–50%** compared to threshold-only alerting — because responders are paged earlier, with context about budget impact severity rather than a raw metric crossing a line.

For HealthCo: `cardiology-api Availability` entering a "Very High" burn-rate state signals that patient-facing cardiology workflows are degrading before end users experience failures — enabling proactive remediation within the SLA window.

### Compliance Audit Readiness (HIPAA / SOC 2)
- Every SLO rule is version-controlled in Git with a commit history — satisfying the "documented change management" control in SOC 2 Type II.
- Daily digests in Git provide a durable, tamper-evident record of AI-assisted configuration decisions — meeting emerging AI governance requirements for regulated industries.
- Folder-level RBAC separation of `cardiology-api` and `oncology-api` from general SLOs creates an auditable access control boundary without requiring a separate monitoring system.
- Estimated audit prep time reduction: **8–12 hours per audit cycle** by replacing manual alert rule inventory with automated digest exports.

### Alert Fatigue Reduction
The golden signal framework (4 alerts per service, standardized naming) prevents alert sprawl. Without it, teams typically accumulate 10–20 ad-hoc alerts per service, many redundant. The 4-signal model at HealthCo covers inventory-service and order-processor with precisely 8 alert rules combined — vs. an industry average of 15–25 for equivalent services.

Estimated on-call burden reduction: **~2 hours/week** per SRE in reduced false positive investigation time.
