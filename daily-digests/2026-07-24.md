## 3. How Enterprise Customers Use This at Scale

**Golden-signal + SLO alerting (checkout, fraud-detection, payment-gateway, auth, notification, shipping, order-service, inventory-service, order-processor):**
- Enterprises organize these as per-service folders/rule groups (exactly the pattern here) so a page routes unambiguously to the owning team, and so a cross-service firing pattern like today's is visible as a *set* in the alert list rather than buried across dashboards.
- Multi-window SLO burn-rate rules (5m/30m/1h/6h/1d/3d, as configured for order-service, Checkout Success, Cart Performance, Ensemble) let fast-burn page on-call while slow-burn opens a ticket — this is the standard way large orgs avoid paging on every minor blip while still catching slow degradations.
- When 6+ service groups fire together, mature incident-response orgs auto-correlate by shared label (region, cluster, dependency) or by deploy timestamp before creating separate tickets per service — reducing duplicate incident channels.

**Runbook skills:**
- Version-controlled alongside infrastructure-as-code (this repo's own pattern) so alert→runbook mapping survives reorganizations and is reviewable in PRs, rather than living in a wiki that drifts out of date.

**Daily automated digests:**
- Committed to a GitOps-style repo (as here) for a lightweight, timestamped audit trail reviewed in a daily platform-team standup — valuable specifically *because* it re-queries live state every run instead of trusting cached assumptions, which is what caught today's alert-count jump from 8 to 36.
