## 3. How Enterprise Customers Use This at Scale

**SLO and golden-signal alerting (aci-*, order-service, checkout performance)**
Large enterprises typically layer alerting: fast-burn SLO rules page the owning service team immediately, while golden-signal (RED/USE) rules feed a lower-priority dashboard reviewed during business hours. Multi-cluster/multi-region deployments federate these rules per business unit, with a platform team owning the shared rule templates (e.g., the `grafana_slo_*` rule pattern seen here) and application teams owning thresholds and labels.

**Kubernetes fleet-wide monitoring (k8s.rules.*, apiserver availability)**
At scale, these community mixin rules (container CPU/memory, apiserver availability) are typically deployed once per cluster via GitOps/Helm and inherited by every namespace. Platform/SRE teams own the base rule set; AppDev teams add service-specific SLOs on top, avoiding duplicated cardinality across clusters.

**Cloud-provider infra alerts (GCP Cloud SQL, Compute, Pub/Sub)**
Enterprises centralize cloud-provider alerts (like the `cloud-provider---gcp` folder here) under a cloud infrastructure/platform team, separate from application SLOs, so a database or compute incident doesn't get mis-attributed to an application team's error budget.

**AI/LLM cost governance (OpenAI/Anthropic alert folders)**
As AI features roll out organization-wide, mature customers apply the same guardrails seen here — per-provider cost-spike, token-rate, and threshold alerts — centrally, then attribute cost back to individual teams/products via labels, preventing any single integration from causing runaway spend.

**Automated reporting/digests committed to git**
Enterprises use scheduled Assistant/automation digests (like this one) as a lightweight audit trail: every day's configuration and observability state is versioned in source control, giving compliance and platform teams a searchable history without manual note-taking.
