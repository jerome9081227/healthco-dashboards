## 3. How Enterprise Customers Use This at Scale

General patterns (illustrative — not specific to a named customer), tied to what exists in this environment today:

- **Golden-signal + SLO burn-rate alerting**: Large orgs standardize a single alert-rule template (error rate, latency p95/p99, traffic, saturation) generated per service via CI/CD or Terraform, then layer Grafana SLOs with multi-window burn-rate alerts (5m/30m/1h/.../3d) on top so paging thresholds map to error-budget consumption, not raw metric noise.
- **Federated ownership**: Platform engineering owns the alerting template and SLO recording-rule library; individual service teams (checkout, cart, inventory, shipping) own their own thresholds and on-call rotation within that template — this mirrors the per-service folder structure already visible here (`ffpfy4qn04um8b`, `cfhxob0gc5zpcb`, etc.).
- **Multi-cluster/multi-cloud**: GCP infra alerts (Cloud SQL, Compute Engine, Pub/Sub) plus Kubernetes recording rules (`k8s.rules.*`) are typically centralized in one Grafana Cloud stack even when workloads span clusters/regions, using consistent label conventions (`namespace`, `cluster`) for cross-cluster rollups.
- **AI/LLM cost governance**: As enterprises adopt LLM-backed features, FinOps/platform teams add anomaly and threshold alerts per provider (token rate, daily cost spike, request duration) — the same pattern already present for Anthropic/OpenAI here — routed to a dedicated cost-alerts contact point separate from production paging.
- **Cardinality/retention discipline**: At scale, teams cap high-cardinality labels (pod, request ID) out of alerting rules, rely on recording rules for expensive aggregations (as seen in the `grafana_slo_*` and `k8s.rules.*` families here), and set log/trace retention by compliance tier rather than one blanket policy.
