## 3. How Enterprise Customers Use This at Scale

### Multi-Tenant SLO Architecture
**Pattern**: Large healthcare organizations run 50-200 SLOs across service boundaries (patient portals, EHR integration, billing, clinical decision support). Each SLO follows the 2-alert, 11-recording-rule pattern seen here, generating ~650-2600 recording rules total.

**Team Structure**: Platform SRE teams own the SLO framework and recording rule infrastructure. Service teams (Patient Access, Clinical Integration, Revenue Cycle) own individual SLO definitions and thresholds.

**Operational Workflow**: Centralized Prometheus federates recording rules from edge clusters. Alertmanager routes burn rate alerts to service-specific PagerDuty/Opsgenie integrations. Weekly SLO review meetings use error budget dashboards to prioritize reliability work.

**Volume Considerations**: Recording rules are pre-aggregated (5m resolution) to control cardinality. A 100-service deployment generates ~1M active series from SLO recording rules alone. Prometheus remote write to Grafana Cloud Metrics provides 13-month retention for compliance reporting.

### GCP Infrastructure Monitoring at Scale
**Pattern**: Multi-project GCP monitoring with centralized Cloud Monitoring export to Grafana Cloud. Customers run 500-5000 CloudSQL instances, 200-2000 Compute Engine VMs, and 50-200 PubSub topics.

**Team Structure**: Infrastructure teams own base alerts (CPU, memory, disk, connections). Application teams configure per-database thresholds via Terraform/Jsonnet. Database administrators receive severity-filtered notifications (critical only).

**Operational Workflow**: Alerts include runbook URLs pointing to internal wikis. On-call engineers acknowledge in PagerDuty, which silences Grafana alerts automatically via bidirectional sync. Post-incident, CloudSQL alerts cross-reference with application SLO violations to quantify patient impact.

**Cardinality Management**: GCP exporter generates 50-100 series per CloudSQL instance. Large deployments use metric relabeling to drop internal labels (`project_id`, `instance_id` retained; `zone`, `replica_index` dropped for aggregates).

### Frontend Observability for Patient Portals
**Pattern**: Grafana Faro instruments React/Angular patient portals. Error counts and Web Vitals flow to Grafana Cloud (separate stack from infrastructure to isolate PHI). 10M+ monthly active users generate 500M-2B frontend events.

**Team Structure**: Frontend engineers own error alerting and Web Vitals SLOs. Product teams set LCP thresholds based on patient satisfaction surveys. Security teams monitor error patterns for potential data leakage or attack indicators.

**Operational Workflow**: Errors exceeding 1% of sessions trigger immediate triage. LCP degradation (p75 > 2.5s) triggers performance sprints. Weekly reports correlate Web Vitals with patient appointment completion rates (business KPI).

**Data Sampling**: Production traffic sampled at 10% for performance, 100% for errors. Session replays enabled only for error sessions to minimize storage (HIPAA minimum necessary principle). 30-day retention for events, 90-day for aggregated metrics.

### Golden Signals for Microservices
**Pattern**: 20-200 microservices per healthcare enterprise, each with 4 golden signal alerts (latency p99, traffic absence, error rate, saturation). Customers generate 80-800 core alerts plus variations for critical endpoints.

**Team Structure**: Platform teams provide alert templates and Prometheus rule libraries. Service owners instantiate alerts via Helm charts or Terraform. On-call rotation follows service ownership boundaries.

**Operational Workflow**: Traffic absence alerts fire within 5 minutes of deployment failures, preventing silent rollout issues. Latency alerts correlate with database query time (CloudSQL alerts). Saturation alerts trigger auto-scaling in GKE before user impact.

**High Cardinality Control**: Error rate alerts aggregate by `service`, `environment`, `method` only — not by user ID, session ID, or patient ID. Latency histograms use 15 buckets (not default 26) to reduce series count. Per-endpoint alerts limited to top 10 trafficked routes.

### Investigation and Incident Tooling
**Pattern**: 50-500 investigations per quarter for enterprise customers. Investigations auto-trigger from PagerDuty webhooks (P1/P2 incidents), SLO burn rate alerts, and manual requests via Slack commands.

**Team Structure**: SRE/incident commander roles initiate investigations. Assistant summarizes signals (metrics, logs, traces) and suggests probable causes. Post-incident reviews reference investigation transcripts for RCA documentation.

**Operational Workflow**: Investigation output feeds directly into Jira/Linear tickets. Compliance teams reference investigation IDs in audit responses. Long-term pattern: investigation findings become runbook skills for future automation.

**Scale Considerations**: Investigations limited to 7-day lookback windows to control query costs. Trace sampling at 5-10% ensures example traces available without overwhelming storage. Log queries scoped to specific services (`service_name` label) to avoid full-index scans.
