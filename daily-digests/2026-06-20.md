## 3. How Enterprise Customers Use This at Scale

### SLO Monitoring Architecture at Scale

**Multi-Team Ownership**
Large healthcare systems (Epic, Cerner integrators, regional hospital networks) run 50-200 SLOs across patient scheduling, EHR sync, imaging workflows, and billing pipelines. Each SLO maps to a service team:
- **Platform SRE**: Owns infrastructure SLOs (Cloud SQL availability, GCE uptime, PubSub delivery latency)
- **Application Teams**: Own business-critical SLOs (Checkout Success = appointment booking completion, Cart Performance = prescription cart checkout)
- **Data Engineering**: Owns data pipeline SLOs (ETL job success rate, replication lag under 5s)

**Burn Rate Alert Routing**
The "Very High" vs "High" burn rate distinction routes to different escalation tiers:
- Very High (multi-window fast burn) → immediate PagerDuty page to primary on-call + auto-open incident
- High (slower burn) → Slack warning to secondary on-call + optional manual escalation
This pattern prevents alert fatigue while maintaining 99.9% SLA coverage for patient-facing services.

**Folder Organization & RBAC**
All SLO rules living in folder `cfhxob0gc5zpcb` suggests a centralized SLO workspace. At scale, enterprises enforce:
- Folder-level RBAC: AppDev teams can view SLOs but only SRE can modify burn rate thresholds
- Namespace isolation: `slo-prod`, `slo-staging`, `slo-dev` folders prevent cross-environment alert pollution
- Compliance tags: Alert rules tagged `hipaa:true`, `sox:true` for audit trail requirements

### GCP Monitoring Federation

**Multi-Cloud & Hybrid Architecture**
HealthCo's GCP-specific alerts (Cloud SQL, Compute Engine, Pub/Sub) indicate a GCP-primary architecture. Enterprise healthcare customers typically run:
- **GCP**: HIPAA-compliant workloads (PHI-handling APIs, FHIR servers, patient portals)
- **AWS**: Legacy EMR integrations via HealthLake
- **On-prem**: Core EHR systems (Epic, Cerner) with cloud sync layers

Grafana becomes the unified pane of glass, federating:
- GCP Cloud Monitoring → Prometheus remote write
- AWS CloudWatch → Grafana CloudWatch data source
- On-prem Prometheus → federated scrape or remote write to Grafana Cloud

**Cloud SQL Replication Topology**
`GcpCloudSQLLagSecondsBehindMaster` monitoring supports read-heavy architectures:
- **Primary (us-central1)**: Write-heavy patient intake, order creation
- **Read Replicas (us-east1, us-west1)**: Reporting dashboards, clinician read queries, analytics workloads
Lag spikes indicate replica CPU saturation (solution: vertical scaling or read pool sharding) or network issues (solution: same-region replica placement).

### Frontend Observability at Enterprise Scale

**RUM Data Volume**
Two Faro applications (Front end store, Ensemble) generate:
- ~10K-100K sessions/day (small regional practice → large hospital network)
- ~1M-10M page views/day at scale
- ~100GB-1TB/month of RUM telemetry (browser errors, vitals, user flows)

**Cardinality Management**
Web Vitals alerts group by `page`, `route`, or `user_agent` dimensions. At scale, enforce:
- Drop low-traffic routes (<100 sessions/day) from high-resolution aggregation
- Sample non-critical user agents (crawlers, monitoring bots)
- Separate patient-facing vs admin-facing apps into different Faro instances to prevent cross-contamination

**Core Web Vitals & Business Metrics Correlation**
LCP (Largest Contentful Paint) monitoring ties to patient portal abandonment rates:
- LCP <2.5s (Good) → ~95% appointment booking completion
- LCP 2.5-4s (Needs Improvement) → ~85% completion (10% drop)
- LCP >4s (Poor) → ~70% completion (25% drop = revenue loss)
Enterprises set LCP SLOs at p75 <2.5s and alert on p95 >4s.

### Golden Signals Implementation Patterns

**Service Mesh Integration**
Inventory-service and order-processor Golden Signals suggest Istio or Linkerd instrumentation:
- **Latency (p99)**: Derived from `istio_request_duration_milliseconds` histogram
- **Traffic**: `rate(istio_requests_total[$__rate_interval])`
- **Errors**: `rate(istio_requests_total{response_code=~"5.."}[$__rate_interval])`
- **Saturation**: Pod CPU/memory from `container_cpu_usage_seconds_total`, `container_memory_working_set_bytes`

**Alert Threshold Evolution**
Initial Golden Signals baselines:
- Latency: p99 <500ms (too permissive for checkout flows)
- Errors: >1% (too high for critical paths)
- Saturation: CPU >80%, Memory >90%

After 3-6 months of production data, teams tighten:
- Checkout flow latency p99 <200ms (SLO-derived)
- Error rate >0.1% for patient-impacting APIs
- Predictive saturation: alert at 70% CPU if 1h trend forecasts >90%

### PubSub & Async Workflow Monitoring

**Message Queue Backlog Management**
`GcpPubSubNumUndeliveredMessages` and `GcpPubSubUnackedMessageAge` monitor async job queues:
- **Use case**: Patient order submitted → PubSub message → order-processor consumer → pharmacy notification
- **Failure mode**: Consumer crash → messages pile up → pharmacy doesn't receive orders → care delay

**Multi-Subscription Architecture**
Large deployments run 10-50 Pub/Sub subscriptions per topic:
- **Topic**: `patient-orders`
- **Subscriptions**: `order-processor-prod`, `order-processor-staging`, `analytics-pipeline`, `audit-log-archiver`
Each subscription needs independent `NumUndeliveredMessages` and `UnackedMessageAge` alerts with subscription-specific thresholds.

**Dead Letter Queue Pattern**
When `UnackedMessageAge` exceeds retry limit (e.g., 10 minutes), messages route to DLQ:
- Alert fires: "DLQ depth >100 messages"
- Runbook: Inspect DLQ for malformed payloads, fix schema validation, replay from DLQ to main queue
This prevents poison messages from blocking healthy message processing.
