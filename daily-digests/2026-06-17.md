## 3. How Enterprise Customers Use This at Scale

### SLO Management & Error Budget Policy

**Architecture Patterns**:
- Multi-product SLO hierarchies: customer-facing SLOs (checkout, cart) backed by dependency SLOs (inventory, order-processor, payment gateway)
- Federated SLO ownership: product teams own customer SLOs, platform SRE owns infrastructure SLOs (database, compute, network)
- Multi-cluster deployments aggregate SLI data from regional Prometheus instances using Grafana Mimir global view

**Operational Workflows**:
- Weekly error budget reviews drive sprint planning — teams below 90% remaining budget freeze feature work
- Burn rate alerts route to different escalation paths: Very High → immediate page + war room, High → async Slack notification + ticket
- SLO recording rules (the 11-rule chain per SLO) pre-compute expensive percentile queries, enabling real-time dashboards without query load

**Team Structures**:
- Product Engineering owns SLO definitions and objectives (what to measure, what % target)
- SRE owns SLI instrumentation and recording rule performance (how to measure efficiently)
- On-call rotation explicitly includes "SLO review" as a handoff ritual

**Volume Considerations**:
- Recording rules reduce cardinality: raw `http_requests_total` might have 50k series, but `grafana_slo_sli_5m` collapses to dozens
- 30m, 1h, 2h, 6h, 1d, 3d recording rules support multi-window alerting without 6x query cost
- Error budget burn rate calculations evaluate 4 windows in parallel (short + long) — recording rules make this sub-second

### Golden Signals Microservices Monitoring

**Architecture Patterns**:
- Service mesh integration: latency p99, error rate, and saturation metrics auto-discovered from Istio/Linkerd telemetry
- Horizontal consistency: every service has identical 4-signal alert structure, making oncall playbooks transferable
- Cross-cluster aggregation: inventory-service alerts evaluate metrics federated from us-east, us-west, eu-central Prometheus instances

**Operational Workflows**:
- Traffic absence alerts trigger automated canary rollback before customers notice
- Saturation alerts (CPU/memory approaching limits) auto-scale pods via Kubernetes HPA integrations before latency degrades
- Error rate alerts link directly to Loki log drilldowns pre-filtered to the alerting service + time window

**Team Structures**:
- Service owners author alert thresholds based on load tests and historical p99 baselines
- Platform team maintains alert rule templates and CI/CD pipelines that generate rules from service definitions
- Incident commander runbooks key off alert names: `inventory-service-latency-p99` → "Check database connection pool saturation, review recent deployment"

**Volume Considerations**:
- 8 rules × 50 microservices = 400 alert rules — Grafana folders organize by domain (payments/, fulfillment/, identity/)
- Alert deduplication via notification policies: group by `service` label with 5min group_wait prevents alert storms during widespread outages
- Cardinality management: latency alerts use `le="0.5"` histogram bucket queries, not unbounded `histogram_quantile()` across all buckets

### Frontend Observability (Faro)

**Architecture Patterns**:
- Multi-application monitoring: separate Faro apps per customer-facing property (store, ensemble, admin portal)
- Geographic segmentation: Web Vitals thresholds differ by region (North America LCP < 2.5s, international < 4s due to CDN coverage)
- Real User Monitoring (RUM) correlated with synthetic checks: Faro errors cross-reference against Grafana Synthetic Monitoring probe failures

**Operational Workflows**:
- LCP degradation alerts trigger automatic CDN cache invalidation workflows before manual investigation
- Error count spikes correlate with backend deployment events via Grafana annotations
- Weekly Core Web Vitals reports feed into product prioritization: consistent LCP issues = infrastructure sprint work

**Team Structures**:
- Frontend engineers own Faro instrumentation and error grouping rules
- DevOps owns alert routing and synthetic monitoring correlation
- Product management consumes aggregated Web Vitals dashboards for user experience OKRs

**Volume Considerations**:
- Session sampling: 100% error capture, 10% performance trace sampling, 1% session replay recording
- 30-day retention for Faro metrics, 7-day for high-cardinality session data to control storage costs
- Geographic rollup: raw metrics by `country_code`, aggregated views by `continent` to reduce dashboard cardinality

### GCP Cloud Provider Monitoring

**Architecture Patterns**:
- Multi-cloud observability: GCP metrics via Stackdriver exporter, AWS via CloudWatch exporter, unified in Prometheus
- Resource tagging: CloudSQL instances labeled with `env=prod`, `app=healthcare-records`, `compliance=hipaa` for filtered alerting
- Cross-account monitoring: platform team Grafana instance queries metrics from 15 GCP projects via service account federation

**Operational Workflows**:
- Replication lag alerts prevent read-after-write inconsistencies critical for healthcare records
- Aborted connection alerts indicate application connection pool misconfigurations or credential rotation issues
- Disk usage alerts trigger automated snapshot creation + storage tier migration before emergency resizing

**Team Structures**:
- Cloud FinOps team owns cost dashboards using same CloudSQL metrics (CPU × instance type = $/hour)
- Database SRE owns CloudSQL performance tuning based on active connection and memory pressure alerts
- Security team consumes connection failure metrics for anomaly detection (credential stuffing, unauthorized access)
