## 3. How Enterprise Customers Use This at Scale

- **Golden-signal + SLO rule groups (per service):** Large enterprises standardize a rule-group template (error rate, latency, traffic, saturation + multi-window burn rate) and generate it per service via CI/Terraform, so every new microservice inherits consistent alerting without manual authoring. Platform engineering owns the template; AppDev teams own thresholds/labels for their service.
- **Multi-team ownership model:** SRE/platform teams own cluster-wide rules (Kubernetes resource rules, apiserver availability); service teams own their golden-signal and SLO groups; a cost/FinOps function owns LLM usage and cloud-provider (GCP) cost alerts. Notification policies route by team label rather than a single shared on-call rotation.
- **Federated/multi-cluster setups:** Kubernetes mixin-style rules (`k8s.rules.*`, `kube-apiserver-availability`) are typically deployed identically across clusters via GitOps, with cluster/namespace labels used to de-duplicate and roll up at a central Grafana Cloud tenant.
- **Volume/cardinality management:** Usage alerts like the "80% over 80,000 series" attributed-metrics rule seen here are how enterprises catch cardinality growth before it hits contract limits — paired with Adaptive Metrics to auto-aggregate low-value series.
- **Runbook lifecycle:** Skills like "Prometheus alert investigation" are versioned alongside dashboards/alerts in git, reviewed on a cadence, and linked directly from alert annotations so responders land on the exact triage steps instead of searching wikis.
- **Digest/automation pattern:** Scheduled Assistant automations (like this one) that write structured Markdown to a git-backed docs repo give enterprises an audit trail of "what changed and why" without requiring a human to write it up manually each day.
