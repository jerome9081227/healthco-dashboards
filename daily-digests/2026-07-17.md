## 2. Key Learnings

### Loki Queries Are Valid Alert Rule Data Sources in Grafana Terraform
The `grafana_rule_group` resource accepts `datasource_uid` pointing to a Loki instance. The `model` block wraps the LogQL expression as a JSON-encoded string. The `expr` lives inside the `jsonencode({})` block, same structure as PromQL-based rules, but with `type = "loki"` in the datasource object. This is not prominently documented — it must be inferred from provider source examples.

### Three-Block Alert Rule Pattern: Query → Reduce → Threshold
Every Grafana alert rule that evaluates a scalar condition against a time-series query follows the same three-data-block pattern:
1. **Block A** — raw query (Loki, Prometheus, etc.) with a real `datasource_uid`
2. **Block B** — reduce expression (`datasource_uid = "__expr__"`, type `reduce`, reducer `last`) collapsing the series to a scalar
3. **Block C** — threshold expression (`datasource_uid = "__expr__"`, type `threshold`) evaluating B against a numeric comparator

This pattern is reusable for any signal type.

### `health=error` on New Alert Groups Means Rule Configuration, Not Service Failure
When a newly created alert rule group shows `health=error` on all rules simultaneously (as seen with inventory-service and order-processor golden signals), this almost always indicates a datasource reference error or a query syntax issue — not an actual service outage. The correct triage path: check the rule's query expression and datasource UID before paging on-call.

### HCL Syntax Is Unforgiving About Indentation in Nested Blocks
The `relative_time_range` blocks inside `data {}` blocks require consistent indentation and explicit `{` on the same line as the block keyword. GitHub web edits and AI-generated code both introduced misalignments. Always run `terraform validate` and `terraform fmt` before pushing.

### Placeholders Must Be Replaced Before `terraform apply`
The correct folder UID for the frontend observability alerts folder is `ffibotdlti2v4a`. Pattern: always discover the real UID from Grafana (`alerting_manage_rules` → `folder_uid`) before writing Terraform — never use placeholder strings.

### Threshold Calibration Is Iterative for Cross-Service Log Queries
The wide selector `{service_name=~".+"}` aggregates error logs across all services simultaneously. A low initial threshold generates false positives from background noise. Threshold of 10 is appropriate for this mixed-traffic environment; production tuning should use a 7-day p99 baseline of idle noise.

## 3. How Enterprise Customers Use This at Scale

### Alert Rules as Code at Enterprise Scale
Large enterprises (500+ engineers, 1000+ services) use the Grafana Terraform provider as the **only** path for creating alert rules in production — the Grafana UI is read-only for production alert folders. The workflow is:
- All alert rules live in a dedicated GitOps repo (`monitoring-as-code`)
- PRs require approval from the on-call team lead and pass a `terraform plan` CI check
- `for_each` over a services variable map generates all four golden signal rules per service automatically — adding a service to `terraform.tfvars` and merging the PR creates full coverage with no UI interaction
- Folder UIDs map to team namespaces, enforcing RBAC boundaries at the infrastructure layer

### Cross-Service Log Alerting as a Tier-0 Canary
Enterprise microservice architectures maintain a single "canary" alert that watches aggregate error log rate across all services. If it fires, it signals a systemic failure (shared infrastructure, deployment gone wrong, dependency outage) rather than a single-service regression. The pattern `sum(count_over_time({service_name=~".+"} |~ "(?i)error" [5m]))` is standard. At scale:
- Alert routes to `#platform-canary` Slack channel with high urgency
- Feeds into IRM auto-incident creation for Severity 1 escalation
- Threshold is environment-specific: dev=50, staging=20, prod=10 (or ML anomaly detection)

### Clinical Service SLO Separation by Folder
Healthcare enterprises typically segregate SLO folders by regulatory domain. Clinical APIs (patient-facing, HIPAA-scope) live in isolated Grafana folders with stricter access controls and dedicated burn rate notification policies routing to clinical on-call, not the general platform team. The HealthCo pattern — `afmhi9j11jwg0c` for cardiology, `efmhi9j1bjhttc` for oncology — mirrors this architecture. At scale, a folder per clinical department allows department-level ownership of SLO targets without shared-folder access risk.

### Multi-Environment Threshold Management via Terraform Variables
Rather than hardcoding thresholds, enterprise modules define `var.error_log_threshold` per environment in `terraform.tfvars`. The same module is called once per environment with different threshold values — eliminating threshold drift between environments. Production is always more sensitive than staging, enforced by the variable map, not by convention.

### Dual-Automation Digest Pattern
Running two automations (11:00 PM scan + 11:50 PM commit) is an enterprise-grade pattern for separating data collection from artifact generation. The 11:00 PM run surfaces early-day learnings while activity is fresh; the 11:50 PM run produces the authoritative end-of-day record with live alert state and final counts. Enterprises extend this to: daily → weekly rollup → sprint retrospective, each feeding the next level.

### HCL Linting in CI Pipelines
Enterprises run `terraform validate` and `terraform fmt --check` as required CI gates on every PR. Common stack: `pre-commit` hooks with `terraform_fmt`, `terraform_validate`, and `tflint` for provider-specific rule validation. This catches the class of indentation and placeholder errors seen in today's fix commits before they reach the main branch.

**Customer-facing framing:** "We now have formal, measurable uptime and latency commitments on our clinical APIs — the same rigor we apply to our eCommerce checkout flow. When those APIs degrade, we know within minutes, not when a clinician calls the help desk."

### Unified Log-Based Alert Coverage Reduces Mean Time to Detect (MTTD)
Before the new cross-service log alert rule, HealthCo's alerting covered infrastructure metrics (GCP Compute, Cloud SQL) and SLO burn rates, but had no cross-service log error signal. A deployment causing log error rate to spike across 5 services simultaneously would not have fired until the SLO burn rate caught up — typically 5–15 minutes later. The new rule fires within **5 minutes of the first spike**, cutting MTTD by 10+ minutes for systemic failures.

**Customer-facing framing:** "We added a cross-service error log canary that detects platform-wide failures 10 minutes before SLO burn rates catch them. In a healthcare environment where uptime affects patient-facing workflows, that's 10 minutes less exposure per incident."

### Alert Rules as Code Creates an Auditable Change History
Every alert rule change now lives in Git with a commit author, timestamp, and message. This satisfies **SOC 2 Type II** and **HIPAA** change management controls directly — the GitHub PR approval workflow is the approval record. No manual screenshots or spreadsheet documentation required.

**Customer-facing framing:** "Our monitoring configuration is version-controlled and PR-gated, identical to application code. Audit evidence for change management is generated automatically — compliance work that used to take hours per audit cycle is now zero."

### Zero-Touch Alert Coverage for New Services
The `for_each` pattern in `alerts.tf` means adding a new service to the service catalog generates four golden signal alert rules automatically on PR merge. This eliminates alert coverage gaps during rapid service growth — a common failure mode in scaling organizations.

**Customer-facing framing:** "When we onboard a new service, it has full alert coverage on day one. The platform team is not a bottleneck. Coverage scales with the business."
