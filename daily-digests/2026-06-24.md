## 3. How Enterprise Customers Use This at Scale

### Multi-Version Digest Pipeline
Large enterprise platform teams run multiple digest jobs per day:
- **Morning digest (7:00 AM ET)**: Surfaces overnight alert activity, open incidents, on-call handoff summary — consumed by the incoming on-call engineer
- **EOD digest (6:00 PM ET)**: Captures what was configured, deployed, or changed during business hours — consumed by engineering leads
- **Nightly canonical digest (11:50 PM ET)**: Full daily state snapshot committed to GitHub as the authoritative operational record
- **Weekly rollup (Sunday 11:00 PM ET)**: Synthesizes 7 daily digests into a trend report committed to the repo and posted to engineering leadership Slack

All jobs run as Grafana Assistant automations on cron schedules, committing to the same GitHub repo under date-stamped paths in a single `daily-digests/` directory.

### Skills as a Tiered Organizational Knowledge Base
Enterprise teams build a skills knowledge base with a defined tier structure:
- **Tier 1 — Environment Reference**: Datasource UIDs, service topology, alert rule UIDs, naming conventions — used by all automations as foundational context
- **Tier 2 — Triage Runbooks**: One skill per alert rule, linked via alert annotation `runbook_url` — surfaced at alert fire time by enrichments
- **Tier 3 — Architecture Decision Records**: ADRs as skills — the AI assistant references them when suggesting configuration changes, preventing drift from documented decisions

At 50+ services, the skills knowledge base becomes the primary mechanism for maintaining consistent automation output without prompt re-engineering. Teams assign ownership of skills the same way they assign codebase ownership.

### GitHub as Observability-as-Code Repository
Enterprise platform engineering teams use GitHub repos as the authoritative store for observability configuration:
- Alert rules provisioned via Grafana Terraform Provider, committed to `alert-rules/` in the same repo
- Dashboard JSON exported and version-controlled in `dashboards/`
- Daily digests committed to `daily-digests/` — full operational history growing automatically
- SLO configuration in `slos/` — change-reviewed via PR gate before applying to production
- PR-based change review for alert rule modifications, enforcing a code review discipline on production alert changes

This pattern turns the observability stack into a versioned, auditable system — the same discipline applied to application code.

### SLO Error Budget as a Product Decision Framework
At enterprise scale, SLOs drive product investment decisions:
- Error budget burn rate dashboards are presented in product reviews to justify reliability sprint vs. feature velocity
- When error budget drops below 50%, a formal reliability sprint is triggered, tracked in the same GitHub repo as the observability config
- `cardiology-api` and `oncology-api` SLOs map to patient-facing service commitments in SLAs — error budget burn is a contractual signal, not just an operational one
- Platform leadership gets a weekly reliability briefing generated by the Sunday rollup automation — no manual slide preparation required

### Digest → PR Description → Deployment Pipeline Integration
Advanced enterprise teams wire Grafana Assistant automations into the CI/CD pipeline:
- Pre-deploy automation runs a snapshot of current SLO state and commits it to the PR as observability context
- Post-deploy automation runs again, diffs before/after, and posts the delta to the PR as a comment
- Failed SLO burn rate after deploy triggers automatic rollback consideration via a webhook integration
- This pattern closes the loop between observability and delivery — Grafana becomes an active participant in the deployment pipeline, not a passive monitor
