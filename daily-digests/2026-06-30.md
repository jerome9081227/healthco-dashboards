### Skills Are the Long-Term Memory Layer for AI-Assisted Work
Grafana Assistant has no persistent memory across sessions by default. Skills solve this. The pattern:
1. Work happens in a session
2. Key context is encoded into a skill (HealthCo Reference, Daily Learnings, etc.)
3. Future sessions load the skill → context is restored
4. The assistant operates as if it has continuity

This is distinct from the Grafana Assistant "memories" feature (which stores preferences) — skills store **structured operational knowledge** that the assistant can act on, not just recall.

## 3. How Enterprise Customers Use This at Scale

### The 3-Arrow / Daily Digest Pattern at 500+ Engineer Orgs
Large enterprises run this pattern at team or squad level, not individual level:
- **Platform engineering team** runs a digest automation for every on-call rotation handoff (daily or weekly)
- **SRE teams** use the structured output to build post-incident knowledge bases automatically — every incident investigation becomes a 3-arrow entry for "how we found it, how we fixed it, what Grafana did that nothing else could"
- **FinTech/HealthTech compliance teams** use the GitHub commit history as an audit trail — every configuration change is committed with a timestamp and message, satisfying SOC 2 Type II change management controls

**Architecture at scale:**
```
Per-squad automations (daily digest) → central GitHub repo (main branch, protected)
     → PR review by platform team (optional) → merged into org-wide knowledge base
```

### Skills as Organizational Memory at Scale
At large orgs, skills become **runbooks-as-code**:
- Skills are scoped to `tenant` for org-wide visibility
- Platform teams own "system skills" (infrastructure runbooks, query templates)
- Individual engineers own personal skills (team-specific context, personal shortcuts)
- Skills reference dashboards, datasource UIDs, alert rule names — they are queryable context, not static documents

**Volume consideration:** An enterprise running 50+ squads on Grafana Cloud can have hundreds of skills. The `search_skills` semantic search capability means engineers don't need to know skill names — they search by intent. This mirrors how enterprise knowledge management works: nobody knows every document, but everyone can find what they need.

### GitHub MCP as a GitOps Compliance Layer
Enterprises use the GitHub MCP not just for convenience — they use it because it makes AI actions auditable:
- Every commit has a SHA, author, timestamp, and message
- Diff history shows what the AI changed vs. what a human changed
- Branch protection rules and PR gates can be applied identically to AI-generated and human-generated changes
- This is the answer to "how do we let AI make changes without losing control?"

**Team structure that works:**
- Platform team owns the repo and branch protection rules
- Individual engineers trigger AI commits to feature branches
- PRs are reviewed by humans before merge to main
- This creates a **human-in-the-loop GitOps workflow** where AI does the work and humans retain control

### Multi-Signal Alert Coverage at Scale (HealthCo Pattern)
The HealthCo alert inventory (58+ rules, 39 datasources) mirrors a pattern common in enterprise healthcare tech:
- **Infrastructure layer**: GCP Cloud SQL, Compute Engine, Pub/Sub (platform-level SLAs)
