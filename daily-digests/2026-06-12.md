- Seasonal traffic (flu season, open enrollment)

## 3. How Enterprise Customers Use This at Scale

### SLO-Based Alerting Architecture

**Multi-Team Federated Ownership**
- **Platform SRE**: Owns the SLO framework itself (Grafana SLO plugin config, recording rule infrastructure, burn rate alert templates)
- **Service Teams**: Own individual SLO definitions (checkout team defines CHeckhout Success objectives, cart team owns Cart Performance SLO)
- **Centralized Observability Team**: Maintains the metrics pipeline (Prometheus federation, Grafana Mimir for long-term storage, cross-region query routing)

**Production Pattern: Nested SLO Hierarchies**
Large enterprises build 3-layer SLO trees:
1. **User-Facing SLOs** (what customers experience) — CHeckhout Success = composite of all checkout flow dependencies
2. **Service SLOs** (component reliability) — Cart Performance, Payment Gateway Latency, Inventory API Availability
3. **Infrastructure SLOs** (platform health) — Database query latency, PubSub message delivery, API gateway throughput

Your Ensemble SLO is the top-layer composite. Cart Performance and CHeckhout Success are service-layer SLOs. The GCP alerts feed infrastructure-layer signals.

**Alert Routing in Multi-Cluster Setups**
- Burn rate alerts fire to **service on-call teams** via PagerDuty/Opsgenie
- Recording rule evaluation failures route to **platform SRE**
- Infrastructure alerts (GCP Cloud SQL, PubSub) route to **infrastructure on-call** with fallback to service teams after 10 minutes

**Cardinality Management for 10,000+ Services**
- Recording rules reduce SLO metric cardinality from `O(requests)` to `O(services × time_windows)`
- For HealthCo's current 3 SLOs × 12 recording rules = 36 pre-aggregated time series (negligible load)
- At enterprise scale (500 SLOs), this becomes 6,000 series vs. billions of raw request metrics

### GCP Infrastructure Monitoring

**Cloud SQL Multi-Region Architecture**
- Primary instance in `us-central1` with read replicas in `us-east1` and `europe-west1`
- Replication lag alerts route to **database SRE team** in primary region, escalate to regional on-call after 5 minutes
- Aborted connections alert fires to **application teams** (usually indicates connection pool misconfig or OOM)

**PubSub Message Flow Monitoring**
- Healthcare enterprises use PubSub for **HL7 FHIR message routing**, **claims processing pipelines**, and **EHR integration queues**
- Message age alerts route to **integration team** (responsible for consumer health)
- Undelivered message count routes to **platform team** (quota/scaling issues)

**Multi-Project GCP Hierarchy**
- Production PHI project: Strict alerting (all alerts page on-call)
- Staging project: Warning-level alerts to Slack channels
- Dev project: Alerts disabled except for quota/cost anomalies

### Machine Learning Observability

- Alerts fire when current behavior deviates >3 standard deviations from forecast
- **AppDev teams** receive alerts for application-layer services (`kg_demo_app`)
