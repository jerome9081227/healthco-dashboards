## 2. Key Learnings

### Loki Queries Are Valid Alert Rule Data Sources in Grafana Terraform
The `grafana_rule_group` resource accepts `datasource_uid` pointing to a Loki instance. The `model` block wraps the LogQL expression as a JSON-encoded string. This is not always obvious from the Terraform provider docs — the trick is that `expr` lives inside the `jsonencode({})` block, same as PromQL-based rules, but with `type = "loki"` in the datasource object.

### Three-Block Alert Rule Pattern: Query → Reduce → Threshold
Every Grafana alert rule that evaluates a scalar condition against a time-series query follows the same three-data-block pattern:
1. **Block A** — the raw query (Loki, Prometheus, etc.) with a real `datasource_uid`
2. **Block B** — a reduce expression (`datasource_uid = "__expr__"`, type `reduce`, reducer `last`) to collapse the series to a scalar
3. **Block C** — a threshold expression (`datasource_uid = "__expr__"`, type `threshold`) that evaluates B against a numeric comparator

This pattern is reusable for any signal type. Memorize it.

### HCL Syntax Is Unforgiving About Indentation in Nested Blocks
The `relative_time_range` blocks inside `data {}` blocks required consistent indentation and explicit `{` on the same line as the block keyword. GitHub-web edits and AI-generated code both introduced misalignments that caused `terraform validate` failures. Always validate HCL before pushing; use `terraform fmt` to normalize.

### Placeholders Must Be Replaced Before `terraform apply`
The initial `folder_uid` was a placeholder string. Terraform applies with a real Grafana provider will reject or misroute rules if the folder UID doesn't exist. The correct UID for today's target folder is `ffibotdlti2v4a`. Pattern: always discover the real UID from Grafana (`alerting_manage_rules` → `folder_uid`, or `read_dashboard_panels` on existing content) before writing Terraform.

### Threshold Calibration Is an Iterative Process
The first threshold value was too low for a cross-service "any error log" query that aggregates `{service_name=~".+"}`. This wide selector picks up all services simultaneously. A threshold of 10 is more appropriate for a mixed-traffic environment; production tuning should use a 7-day baseline window to find the 99th-percentile idle noise floor.

## 3. How Enterprise Customers Use This at Scale

### Alert Rules as Code at Enterprise Scale
Large enterprises (500+ engineers, 1000+ services) use the Grafana Terraform provider as the **only** path for creating alert rules — the Grafana UI is read-only for production alert folders. The workflow is:
- Alert rules live in a dedicated GitOps repo (e.g., `monitoring-as-code`)
- PRs require approval from the on-call team lead and pass a `terraform plan` CI check
- `for_each` over a services variable map generates rules for every service automatically — adding a new service to `terraform.tfvars` and running `apply` creates all four golden signal alerts with no UI interaction
- Folder UIDs map to team namespaces, enforcing RBAC boundaries at the infrastructure level

Today's `for_each` pattern in `alerts.tf` is the template: one Terraform file, one `for_each`, four rules per service (latency, traffic-absent, errors, saturation). Enterprise teams extend this with a fifth rule for log-based anomalies — exactly what `all-services-errors.tf` adds.

### Cross-Service Log Alerting as a Tier-0 Canary
Enterprises with microservice architectures often create a single "canary" alert rule that watches the aggregate error log rate across **all services**. If this fires, it signals a systemic issue (shared infrastructure, deployment gone wrong, dependency outage) rather than a single-service regression. The LogQL query `sum(count_over_time({service_name=~".+"} |~ "(?i)error" [5m]))` is the standard pattern. At scale:
- Teams route this alert to a dedicated Slack channel (`#platform-canary`) with high urgency
- The alert feeds into IRM auto-incident creation for Severity 1 escalation
- Threshold is set per environment: dev=50, staging=20, prod=10 (or use Grafana ML anomaly detection)

### HCL Linting in CI Pipelines
Enterprises run `terraform validate` and `terraform fmt --check` as required CI gates on every PR to the monitoring repo. Common tools: `pre-commit` hooks with `terraform_fmt` and `terraform_validate`, plus `tflint` for provider-specific rule validation. This prevents the class of syntax errors fixed in commits `7730bfe` and `270305b` from ever reaching the main branch.

### Multi-Environment Threshold Management
Rather than hardcoding `params = [10]` in the threshold condition, enterprise Terraform modules define a `var.error_log_threshold` per environment in `terraform.tfvars`. The module is called once per environment (dev, staging, prod) with different threshold values, all from the same `.tf` file. This eliminates threshold drift between environments.

## 4. Real-World Business Impact

### Unified Log-Based Alert Coverage Reduces Mean Time to Detect (MTTD)
Before this rule, HealthCo's alerting covered infrastructure metrics (GCP Compute, Cloud SQL) and SLO burn rates, but had no cross-service log error signal. A deployment that causes log error rate to spike across 5 services simultaneously would not have fired any alert until the SLO burn rate caught up — typically 5–15 minutes later. The new rule fires within **5 minutes of the first spike**, cutting MTTD by 10+ minutes for systemic failures.

**Customer-facing framing:** "We added a cross-service error log canary that detects platform-wide failures 10 minutes before SLO burn rates would catch them. In a healthcare environment where uptime affects patient-facing workflows, that's 10 minutes less exposure per incident."

### Alert Rules as Code Creates an Auditable Change History
Every alert rule change now lives in Git with a commit author, timestamp, and message. This is directly relevant for **SOC 2 Type II** and **HIPAA** compliance, where auditors require evidence that monitoring configurations were reviewed and approved before deployment. The GitHub PR approval workflow is the approval record. No manual screenshots or spreadsheet documentation required.

**Customer-facing framing:** "Our monitoring rules are version-controlled and PR-gated, the same as application code. Audit evidence for change management controls is generated automatically — no extra compliance work required."

### Terraform-Driven Alert Management Scales to Zero-Ops
When the service catalog grows (new microservice onboarding), the `for_each` pattern means the platform team doesn't need to manually create alert rules in the UI. The developer adds one entry to `terraform.tfvars`, opens a PR, and the CI pipeline generates the full golden signal coverage on merge. This eliminates alert coverage gaps during rapid service growth — a common failure mode in scaling organizations.

**Customer-facing framing:** "We have zero-touch alert coverage for new services. The platform team doesn't become a bottleneck when engineering ships fast."
